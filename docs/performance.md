# Performance Tuning

The default configuration generated by `ovpn_genconfig` is a reasonable, safe default and most deployments won't need to touch anything here. If you're on a high-bandwidth link and not seeing the throughput you expect, or clients are experiencing stalls/choppy transfers over a constrained path, the options below can help.

You can get a summary of these options at any time by running:

    docker run --rm --log-driver=none nmaguiar/openvpn help-more

## Socket buffers (`-B` sndbuf / `-R` rcvbuf)

Socket buffers can become a bottleneck when packets arrive faster than OpenVPN can drain them. Check UDP receive errors/drops and effective socket sizes before increasing them; there is no universal bandwidth threshold at which larger buffers help.

    docker run -v /etc/openvpn:/etc/openvpn --rm --log-driver=none nmaguiar/openvpn config -u udp://VPN.SERVERNAME.COM -B 393216 -R 393216

Values are in bytes. `393216` (384KiB) is a reasonable starting point; go up to `1048576` (1MiB) or more for very high bandwidth (1Gbps+) links. It's generally best to set the same value for both.

These options are applied to both the server config and any client configs generated afterwards with `ovpn_getclient`, since OpenVPN recommends matching buffer sizes on both ends.

**Important:** the Docker host's kernel also caps socket buffers via the `net.core.rmem_max` / `net.core.wmem_max` sysctls. If those are lower than the value you request here, the requested size is silently capped. If you don't see an improvement after raising `-B`/`-R`, check (and if needed raise) those sysctls on the host, e.g.:

    sysctl -w net.core.rmem_max=1048576
    sysctl -w net.core.wmem_max=1048576

## Fast I/O (`-F` fast-io)

Avoids an extra syscall on the packet read/write path. It's a small but effectively free win for UDP deployments under sustained traffic. It is **not compatible with TCP** (`-u tcp://...`) — `ovpn_genconfig` will warn and skip it if you request it with a TCP proto.

    docker run -v /etc/openvpn:/etc/openvpn --rm --log-driver=none nmaguiar/openvpn config -u udp://VPN.SERVERNAME.COM -F

## MTU clamping (`-M` mssfix)

Useful when connections establish fine but bulk transfers stall or crawl — a common symptom of a client sitting behind a path with a smaller MTU than usual (mobile/cellular networks, PPPoE, or a VPN running inside another VPN). `mssfix` clamps the TCP MSS seen inside the tunnel so oversized packets are avoided in the first place, rather than being fragmented and reassembled after the fact (which is what the existing `-f`/`fragment` option does).

    docker run -v /etc/openvpn:/etc/openvpn --rm --log-driver=none nmaguiar/openvpn config -u udp://VPN.SERVERNAME.COM -M 1400

Measure the path MTU before choosing a value. The meaning of the size includes OpenVPN overhead and depends on the OpenVPN version and optional `mtu` argument; `1400` is an experiment, not a universally safe setting. This clamps TCP inside the tunnel, not arbitrary inner UDP traffic. With DCO, check the installed version's support and use host firewall MSS clamping where needed.

## Combining options

These can all be combined, along with the rest of `ovpn_genconfig`'s options:

    docker run -v /etc/openvpn:/etc/openvpn --rm --log-driver=none nmaguiar/openvpn config -u udp://VPN.SERVERNAME.COM -B 393216 -R 393216 -F -M 1400

## Changing these on an existing configuration

The `config`/`ovpn_genconfig` command only writes these settings when it (re)generates `/etc/openvpn/openvpn.conf`. If you already have a working setup and don't want to regenerate it, you can edit the directives directly instead:

| Flag | Config directive |
| ---- | ----------------- |
| `-B <bytes>` | `sndbuf <bytes>` |
| `-R <bytes>` | `rcvbuf <bytes>` |
| `-F` | `fast-io` |
| `-M <bytes>` | `mssfix <bytes>` |

Edit the running container's config in place (add missing lines, or change the value if the directive is already there):

    docker exec -it openvpn sed -i '/^sndbuf /d;/^rcvbuf /d' /etc/openvpn/openvpn.conf
    docker exec -it openvpn sh -c 'echo "sndbuf 393216" >> /etc/openvpn/openvpn.conf; echo "rcvbuf 393216" >> /etc/openvpn/openvpn.conf'

Or, if the volume is a host directory (e.g. `-v /etc/openvpn:/etc/openvpn`), just edit `/etc/openvpn/openvpn.conf` on the host with any text editor and add/change the same directives.

These directives are only read at OpenVPN startup, so restart the container for the change to take effect:

    docker restart openvpn

`sndbuf`/`rcvbuf` are best matched on both ends of the tunnel, so if you change them on the server, also add the same `sndbuf`/`rcvbuf` lines to already-issued client `.ovpn` files (or regenerate them with `ovpn_getclient` after updating the server config).

## Opt-in DCO profile (`-O dco`)

Data Channel Offload moves encryption and packet forwarding into the Linux kernel.
Containers share that kernel, so DCO can work with either bridge or host networking.
It is particularly useful when legacy userspace packet processing saturates a CPU
core. It cannot fix a slow client, congested WAN, or inadequate host resources.

Generate a fresh configuration with:

```sh
docker run --rm -v "$OVPN_DATA:/etc/openvpn" nmaguiar/openvpn \
  ovpn_genconfig -u udp://vpn.example.com:1194 -O dco
```

The profile selects `topology subnet`,
`data-ciphers AES-256-GCM:AES-128-GCM:CHACHA20-POLY1305`, and
`allow-compression no`. It omits both server and pushed `comp-lzo no` framing.
Exported clients also receive `allow-compression no`. Use modern clients that
support these directives. Client-side DCO is independent of server-side DCO.

The profile persists in `ovpn_env.sh`. `-O legacy` explicitly returns to the
previous generator behavior. Switching profiles resets the cipher list to that
profile's default unless `-C` is supplied in the same command, in either order.
Regenerating without switching preserves the saved cipher list. DCO rejects TAP,
compression, fragmentation, non-AEAD ciphers, and conflicting raw extras before
replacing the saved configuration. Raw `-e`/`-E`/`-p` options controlling topology,
compression, ciphers, devices, includes, or disabling DCO are deliberately rejected
in this profile; use the dedicated flags where available.

**Migration:** back up the entire configuration volume first. Regeneration
preserves generator settings but does not import manual `openvpn.conf` edits.
Review existing `ccd` files and `ifconfig-push` addresses for subnet topology,
remove incompatible saved extras/settings, and re-export/distribute client
profiles. Switching back also requires checking static addresses and client
profiles. Do not assume a running deployment can change topology without client
reconnections. The generator does not rewrite CCD files.
With DCO, peer forwarding uses kernel routes and firewall rules rather than
OpenVPN's internal client-to-client forwarding. Review peer isolation and
site-to-site `iroute`/route behavior as part of migration.

### Updating an existing server and issued client profiles

Use this procedure after preparing the Linux host module described below. Run
the commands on the Docker host, using an image containing `-O dco` support.
Existing certificates and keys can be reused: **do not run `ovpn_initpki`, `init`,
or recreate users as part of this migration**.

1. Identify the existing configuration volume/bind mount and retain the current
   deployment command or Compose file, image tag/digest, and original client
   profiles. Choose a reconnect window and stop the server before backing up.
   Replace these example values with your existing volume and tested image:

   ```sh
   OVPN_DATA=/etc/openvpn             # Or the existing named Docker volume
   OVPN_IMAGE=nmaguiar/openvpn:performance-test
   umask 077
   docker stop openvpn
   OVPN_BACKUP="openvpn-before-dco-$(date +%Y%m%d-%H%M%S).tgz"
   docker run --rm -v "$OVPN_DATA:/etc/openvpn:ro" \
     --entrypoint tar "$OVPN_IMAGE" -C /etc/openvpn -czf - . > "$OVPN_BACKUP"
   tar -tzf "$OVPN_BACKUP" >/dev/null
   ```

   Confirm the backup commands succeeded before proceeding. The archive contains
   private keys; keep it private. The command works for bind mounts and named
   volumes. Back up any separately mounted CCD/configuration files too.

2. Review `openvpn.conf` and `ovpn_env.sh` in that volume. Regeneration reads
   `ovpn_env.sh`, so changing only `openvpn.conf` does not remove saved conflicts.
   If necessary, edit the existing saved declarations to use `OVPN_DEVICE=tun`,
   `OVPN_COMP_LZO=0`, and `OVPN_FRAGMENT=''`. Remove conflicting entries from
   `OVPN_EXTRA_SERVER_CONFIG`, `OVPN_EXTRA_CLIENT_CONFIG`, and `OVPN_PUSH`, including
   compression, `disable-dco`, explicit topology, and cipher overrides. Preserve
   unrelated routes, DNS, authentication, and other settings. A TAP deployment
   requires a routed network redesign; do not just change its device setting.
   Review manual `openvpn.conf` additions and preserve compatible ones through
   the generator's extra settings. Leave `OVPN_PROFILE` for the generator to set.

3. Regenerate using the saved server URL, port, protocol, and other settings:

   ```sh
   docker run --rm -v "$OVPN_DATA:/etc/openvpn" "$OVPN_IMAGE" ovpn_genconfig -O dco
   ```

   This changes the data-cipher list to the DCO default. To select a different
   AEAD-only list, also supply `-C`. Do not change `-u` merely to opt in: changing
   the hostname can change which server certificate the configuration references.
   Switching TCP to UDP is a separate change requiring matching client and port
   publishing changes.

   Review the resulting configuration and any `ccd/*` files. With subnet
   topology, the second `ifconfig-push` argument is the subnet mask rather than
   a net30 peer address. For example, for an actual `10.8.0.0/24` VPN subnet,
   a reserved static client address could use `ifconfig-push 10.8.0.10 255.255.255.0`.
   Choose an address that does not conflict with the dynamic pool or another
   client. The generator does not perform this conversion or update firewall rules.

4. Export a replacement profile for each **existing certificate name**:

   ```sh
   docker run --rm -v "$OVPN_DATA:/etc/openvpn" "$OVPN_IMAGE" \
     ovpn_getclient my-user > my-user-dco.ovpn
   ```

   Check export success and the generated file before distributing it. Replace
   `my-user` with each existing user/certificate name. Import the new profile in
   the client application, preserving any application-specific proxy, routing,
   or authentication preferences. Existing certificate/key material is reused;
   a passphrase-protected key keeps its passphrase. Use clients that support the
   emitted directives (for Community OpenVPN, 2.5+ supports `data-ciphers` and
   `allow-compression`; actual DCO requires a supported newer client/driver).

   If a profile cannot be re-exported, edit a **copy** of its `.ovpn` file:

   ```conf
   dev tun
   data-ciphers AES-256-GCM:AES-128-GCM:CHACHA20-POLY1305
   allow-compression no
   ```

   Replace existing versions of those directives rather than appending duplicates,
   and match the server's chosen AEAD cipher list. Remove `comp-lzo` (including
   `comp-lzo no`), `compress` (including stub modes), `fragment`, legacy `cipher`/
   `data-ciphers-fallback` overrides, and conflicting `compat-mode` settings.
   Remove a hard-coded `topology net30` or static tunnel `ifconfig` setting so a
   normal `client`/`pull` profile accepts the server's subnet configuration. Do not
   remove the `client` directive, remote endpoint, certificate verification,
   authentication settings, or inline `<ca>`, `<cert>`, `<key>`, `<tls-auth>`, and
   `<tls-crypt>` blocks. Resolve any includes or pull filters that override these
   settings. This recipe is for ordinary generated client profiles, not manually
   addressed point-to-point configurations.

   Remove client-side `disable-dco` only if you also want local client offload and
   that client supports it. A compatible client can continue using userspace
   processing while the server uses DCO; the client does not need the Linux
   server's kernel module.

5. If the existing container already uses the intended image, start it again
   with `docker start openvpn`. Otherwise recreate it with the new image using
   the saved deployment command/Compose configuration, the **same configuration
   volume**, port mappings, devices, capabilities, and other settings. Do not
   delete the volume. Restarting an old container does not update its image.
   Reconnect an updated client and check offload diagnostics, Internet/site
   routes, DNS, static addresses, and peer isolation before migrating all clients.

6. To roll back, stop the server, restore the backed-up configuration/CCD files
   and original client profiles, and restore the previous image/deployment. For
   a clean rollback, restore into an empty replacement volume/directory and point
   the deployment at it rather than overlaying files and retaining new settings.
   Simply running `-O legacy` restores generator defaults, **not** the exact old
   cipher choices, manual edits, CCD assignments, or client profiles.

### Host prerequisites and diagnostics

| Container OpenVPN | Host kernel support |
| --- | --- |
| 2.6.x with DCO enabled in the build | Compatible `ovpn-dco` module (loaded name `ovpn_dco_v2`) |
| 2.7+ with DCO enabled in the build | `ovpn`, upstream from Linux 6.16, or a compatible backport |

The distribution must actually ship/enable the module. Install/load it on the
Linux Docker host, not inside the image; no `--privileged` or `SYS_MODULE`
capability is needed to install modules from the VPN container. Keep the existing
`NET_ADMIN` and `/dev/net/tun` access for normal operation and userspace fallback.
The Dockerfile's floating Alpine base does not guarantee the deployed OpenVPN
version: check `docker exec openvpn openvpn --version` and record the image digest.

`ovpn_run` prints a read-only DCO preflight with the binary version, kernel, module
visibility, and common incompatible settings. You can also run
`docker exec openvpn ovpn_dco_status /etc/openvpn/openvpn.conf`.
Module visibility/build support is **not proof of activation**. OpenVPN's own
startup and peer logs report fallback reasons; check the actual tunnel driver
with `ip -d link show tun0` using a recent iproute2. A DCO-compatible profile is
allowed to fall back to userspace when kernel support is absent.

Sources: [OpenVPN 2.6 DCO](https://github.com/OpenVPN/openvpn/blob/release/2.6/README.dco.md),
[current DCO/kernel compatibility](https://github.com/OpenVPN/openvpn/blob/master/README.dco.md).

## Native Linux host networking

Benchmark `--network host` against bridge networking after checking CPU and DCO.
Host networking removes the bridge and Docker port-publishing/NAT path; it does
not remove VPN egress masquerading. It also puts this image's routing and iptables
changes directly in the host namespace. Use a dedicated test host first.

Example for a native Linux host with egress interface `ens3` and port 1194:

```sh
docker run -d --name openvpn --network host \
  --cap-add NET_ADMIN --device /dev/net/tun \
  -e OVPN_NATDEVICE=ens3 -v "$OVPN_DATA:/etc/openvpn" \
  nmaguiar/openvpn ovpn_run --port 1194
```

Replace `ens3` with the host's egress interface. Check that `ovpn_env.sh` does not
override that variable. Set host IPv4 forwarding (`net.ipv4.ip_forward=1`) and
appropriate firewall INPUT/FORWARD rules; configure IPv6 forwarding separately
if used. Do not pass network sysctls through Docker in host mode. Remove all `-p`
flags. The generator always writes internal port 1194, so another advertised
port requires the matching `ovpn_run --port` override. Avoid tunnel-interface,
VPN-subnet, and port collisions with other host services. Restarting/removing
this image does not clean up host iptables rules it added.

Docker Desktop has an additional VM/network path and its host networking is not
equivalent to native Linux host networking for a TUN VPN. Use native Linux for
production throughput comparisons.
[Docker host networking](https://docs.docker.com/engine/network/drivers/host/)

## Measure before and after

Use [the benchmark harness](../test/README.md#throughput-benchmark) to measure
single/four TCP streams in both directions over an established tunnel. Compare
bridge/DCO-off, bridge/DCO-on, host/DCO-off, and host/DCO-on with the same cipher,
topology, client, path, buffers, and duration. Use the DCO profile in all four
cases and add `ovpn_run --disable-dco` for the server's off cases. This avoids
confounding offload with a cipher or topology change.

Also measure the underlying path without the VPN, using controlled endpoints,
and monitor per-core CPU/softirq load on the Linux host (`mpstat -P ALL 1`), CPU
quotas/throttling, NIC errors, and UDP drops. Kernel offload CPU work may not be
fully charged to the container's `docker stats` CPU figure. Repeat runs and
compare results; same-host client/server tests do not represent WAN throughput.

* **Cipher choice:** benchmark AES-GCM versus ChaCha20-Poly1305 on the actual CPU.
  Hardware AES support matters; AES-CBC in the legacy list is not AEAD and can
  disable DCO. Do not weaken authentication to improve bulk throughput.
* **Compression:** leave it disabled. It adds work, is incompatible with DCO,
  and can expose compression-oracle attacks. Legacy `comp-lzo no` still uses
  compression framing even though outgoing payload compression is disabled.
* **Multi-core scaling:** legacy userspace data processing is constrained by a
  single process's packet loop. DCO changes that architecture. Without DCO,
  multiple instances can distribute clients across cores, but do not accelerate
  a single client tunnel. Remove accidental CPU quotas before scaling out.
